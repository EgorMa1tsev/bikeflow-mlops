# BikeFlow

Прогноз почасового спроса на городской велопрокат в Сеуле. Учебный MLOps-проект: путь от
исходных данных до модели, которая отвечает на HTTP-запросы из Docker-контейнера.

Модель предсказывает, сколько велосипедов возьмут в аренду за конкретный час, по дате, времени и
погоде. Данные — [Seoul Bike Sharing Demand](https://archive.ics.uci.edu/dataset/560/seoul+bike+sharing+demand)
(UCI): 8760 почасовых наблюдений за год, с декабря 2017 по ноябрь 2018.

## Что уже работает

- загрузка датасета с проверкой контрольной суммы, предобработка и проверки качества данных;
- пайплайн данных и обучения в DVC: одна команда воспроизводит всё и пересчитывает только
  изменившиеся стадии;
- разбиение на train / validation / test строго по времени, без перемешивания;
- четыре модели и автоматический выбор лучшей по скользящей валидации;
- трекинг экспериментов в MLflow: параметры, метрики и модель каждого обучения, регистрация
  лучшей модели в реестре;
- единый артефакт модели: предобработка и нейросеть в одном файле;
- REST API на FastAPI с документацией OpenAPI (Swagger);
- журнал прогнозов: каждый запрос, прогноз и версия модели сохраняются, а фактический спрос
  досылается позже;
- поток новых данных: скрипт проигрывает октябрь–ноябрь 2018 через API по часам, с задержкой
  фактического спроса и сценарием управляемого дрейфа;
- расчёт data drift, target drift и concept drift по журналу прогнозов, HTML-отчёты Evidently;
- метрики для Prometheus и готовый дашборд Grafana: нагрузка, ошибка модели, дрейф, переобучения;
- переобучение вручную и автоматически при concept drift: новая модель проходит quality gate и
  только тогда заменяет текущую в реестре MLflow и в API — без перезапуска;
- Docker-образ;
- CI на GitHub Actions: линтер, тесты, сборка образа и проверка API в контейнере.

## Как устроен прогноз

```
JSON-запрос → валидация → время в часовой пояс Сеула → календарные признаки
            → предобработка → нейросеть → прогноз и версия модели → журнал прогнозов

после окончания часа: фактический спрос → журнал → ошибка прогноза
```

Время в запросе обязательно указывается с часовым поясом. Погоду передаёт пользователь.

## Модель и качество

Рабочая модель — нейросеть PyTorch с эмбеддингами для часа, дня недели и сезона
(`mlp_embedding`).

Лучшая модель выбирается по среднему **MAE** на трёх последовательных периодах
(rolling-origin cross-validation): каждый раз модель обучается на прошлом и проверяется на
следующих двух месяцах. Тестовая выборка в выборе не участвует.

| Модель | Средний MAE по трём периодам |
| --- | ---: |
| **mlp_embedding** — нейросеть с эмбеддингами | **386.8** |
| hgb — градиентный бустинг | 416.6 |
| mlp_onehot — нейросеть с one-hot кодированием | 422.1 |
| seasonal_median — медиана по часу и дню недели | 733.8 |

На тестовой выборке (октябрь–ноябрь 2018) рабочая модель показывает **MAE 189.5** и
**WAPE 0.223**. MAE — основная метрика, ошибка в арендах за час. WAPE — дополнительная, ошибка
в долях от суммарного спроса.

Цифры взяты из `reports/model_selection.md`. При обучении на другой системе они могут немного
отличаться.

## Запуск

### 1. Установка

Нужен **Python 3.11** — под него зафиксированы версии пакетов, CI и Docker-образ.

Windows (PowerShell):

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
```

Linux и macOS:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
```

Дальше одинаково на всех системах:

```bash
python -m pip install --upgrade pip
python -m pip install --constraint requirements/runtime-py311.lock torch==2.6.0 --index-url https://download.pytorch.org/whl/cpu
python -m pip install --constraint requirements/runtime-py311.lock -e ".[dev,ml,mlp,dvc]"
```

PyTorch ставится отдельной командой из CPU-индекса: обычная сборка тянет CUDA на несколько
гигабайт, а видеокарта проекту не нужна.

Если Python 3.11 не установлен, окружение можно создать через [uv](https://docs.astral.sh/uv/)
вместо первой команды: `uv venv --python 3.11 --seed .venv` — uv сам скачает Python 3.11.

**Окружение нужно активировать в каждом новом окне терминала.** Признак, что оно активно, —
`(.venv)` в начале строки.

### 2. Данные и обучение

Весь пайплайн описан в `dvc.yaml` и запускается одной командой:

```bash
dvc repro
```

DVC по очереди выполнит четыре стадии `download → preprocess → split → train`: скачает датасет
с UCI, проверит и подготовит данные, разобьёт их по времени, обучит модели и сохранит лучшую.
Около минуты на обычном ноутбуке. Результат — `models/model.joblib` и отчёты в `reports/`.

При повторном запуске DVC пересчитывает только то, что изменилось. После правки параметров сети
в `params.yaml` перезапустится только `train`, после изменения дат разбиения — `split` и
`train`. Файл `dvc.lock` хранит хеши данных, модели и параметров, поэтому по нему видно, на каких
данных и с какими настройками обучена модель в каждом коммите.

```bash
dvc status          # что изменилось с последнего запуска
dvc dag             # схема пайплайна
dvc params diff     # какие параметры изменились относительно последнего коммита
dvc metrics diff    # как изменились метрики
```

Удалённого хранилища DVC нет: датасет публичный и полностью пересоздаётся командой `dvc repro`.

Стадии можно запускать и без DVC, по отдельности:

```bash
python -m bikeflow.ml download     # скачать датасет с UCI
python -m bikeflow.ml preprocess   # проверить данные и привести их к единому виду
python -m bikeflow.ml split        # разбить на train / validation / test по времени
python -m bikeflow.ml train        # обучить модели, выбрать лучшую и сохранить её
```

Команда `python -m bikeflow.ml cv` отдельно показывает сравнение моделей по трём периодам.

### 3. Эксперименты и реестр моделей в MLflow

Каждое обучение автоматически записывается в MLflow — одна запись (run) на запуск:

- параметры из `params.yaml`: seed, даты разбиения, признаки, параметры моделей, способ выбора;
- метрики лучшей модели на validation и test и средний MAE по скользящей валидации для каждой
  из четырёх моделей;
- отчёты о выборе модели;
- сама модель с сигнатурой входа и примером запроса;
- метки с хешем данных и git-коммитом: по ним видно, на каких данных и каком коде обучена модель.

Лучшая модель регистрируется в реестре как новая версия `bikeflow-demand` и получает метку
`champion`.

История экспериментов хранится в файле `mlflow.db` в корне проекта. Открыть интерфейс:

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

и перейти на <http://127.0.0.1:5000>. В разделе **Experiments** → `bikeflow` — все запуски с
параметрами и метриками, их можно сравнивать между собой. В разделе **Models** — версии
зарегистрированной модели.

Чтобы писать в MLflow-сервер вместо локального файла, задайте переменную окружения
`MLFLOW_TRACKING_URI`. Имена эксперимента и модели настраиваются в разделе `tracking` файла
`params.yaml`.

### 4. Проверка качества и прогноз из командной строки

```bash
python -m bikeflow.ml evaluate --split test
python -m bikeflow.ml predict --input data/processed/test.parquet --output reports/predictions.csv
```

Первая команда выводит метрики на тестовой выборке с разбивкой по сезону, выходным и дождю.
Вторая считает прогноз для каждой строки файла.

### 5. API

```bash
uvicorn bikeflow.api.main:app --host 127.0.0.1 --port 8000
```

API загружает модель из `models/model.joblib`. Путь можно изменить переменной окружения
`BIKEFLOW_MODEL_PATH`.

Документация и форма для запросов: <http://127.0.0.1:8000/docs> → `POST /predict` →
**Try it out**. Пример тела запроса:

```json
{
  "prediction_time": "2018-12-01T18:00:00+09:00",
  "temperature_c": 3.5,
  "humidity_pct": 45,
  "wind_speed_m_s": 1.2,
  "visibility_10m": 2000,
  "dew_point_c": -7.0,
  "solar_radiation_mj_m2": 0.0,
  "rainfall_mm": 0.0,
  "snowfall_cm": 0.0,
  "holiday": false,
  "functioning_day": true
}
```

В ответе — прогноз `predicted_rentals`, версия модели `model_version` и номер записи в журнале
`prediction_id`. Запрос без часового пояса или со значениями вне допустимых диапазонов получает
ошибку `422`.

**Журнал прогнозов.** Каждый прогноз сохраняется в `data/predictions.db` (путь меняется переменной
`BIKEFLOW_DB_PATH`). Фактический спрос за час известен только после его окончания, поэтому он
досылается отдельно:

| Эндпоинт | Что делает |
| --- | --- |
| `POST /predictions/{prediction_id}/actual` | записывает фактический спрос, тело `{"actual_rentals": 498}` |
| `GET /predictions?limit=100` | последние прогнозы с фактом и ошибкой, новые первыми |

Оба эндпоинта тоже доступны в Swagger. Подробнее — в [контракте API](docs/contracts/model_api.md).

### 6. Поток новых данных

Скрипт проигрывает историю через запущенный API так, будто данные поступают в реальном времени.
По умолчанию берётся тестовый период — октябрь и ноябрь 2018, модель его не видела. Для каждого
часа отправляется погода в `/predict`, а фактический спрос досылается через час, когда этот час
уже закончился.

В одном окне терминала запустите API (шаг 5), в другом:

```bash
python -m bikeflow.replay                     # весь тестовый период, около минуты
python -m bikeflow.replay --hours 48          # только первые двое суток
python -m bikeflow.replay --interval 0.5      # по полсекунды на час — удобно для демонстрации
```

**Сценарий дрейфа.** Чтобы проверить, как система замечает деградацию модели, можно изобразить
акцию: с выбранной даты вечерний спрос (17:00–21:00) умножается на коэффициент, а погода остаётся
прежней.

```bash
python -m bikeflow.replay --evening-boost 2.5 --boost-from 2018-11-01
```

Модель не знает об акции, поэтому её ошибка растёт при неизменных входах — это concept drift.
Как его обнаружить, описано в следующем разделе.

Адрес API задаётся опцией `--api` или переменной `BIKEFLOW_API_URL`, по умолчанию
`http://127.0.0.1:8000`. Все опции: `python -m bikeflow.replay --help`.

### 7. Дрейф данных и модели

API сравнивает последние 7 суток журнала — часы, для которых уже известен фактический спрос, — с
эталоном: периодом validation вместе с прогнозами модели на нём. Эталон сохраняется в артефакт
модели при обучении, поэтому после переобучения он обновляется сам.

| Вид дрейфа | Что сравнивается | Когда срабатывает |
| --- | --- | --- |
| data drift | распределения погодных признаков (Evidently, расстояние Вассерштейна) | у половины признаков и больше |
| target drift | распределение фактического спроса | расстояние 0.1 и больше |
| concept drift | ошибка модели: MAE за окно, делённая на MAE на validation | больше 1.6 |

**Порог concept drift выбран по данным**: на validation недельная MAE модели ни разу не превысила
1.54 от эталонной, поэтому 1.6 означает «хуже любой недели, которую модель показывала на проверке».
Пороги задаются в разделе `monitoring` файла `params.yaml`.

**Data drift и target drift здесь информационные.** Погода и спрос сезонные, поэтому неделя одного
сезона почти всегда отличается от эталонного периода — это видно в отчёте, но модель при этом может
работать нормально. Concept drift означает, что модель сама стала ошибаться сильнее, — это сигнал к
переобучению.

| Эндпоинт | Что делает |
| --- | --- |
| `POST /drift/check` | проверяет дрейф сейчас, сохраняет результат и HTML-отчёт |
| `GET /drift/latest` | результат последней проверки |
| `GET /drift/report` | HTML-отчёт Evidently — открывается прямо в браузере |

**Демонстрация.** Опция `--check-every 24` запускает проверку после каждых суток потока, как это делал
бы планировщик:

```bash
python -m bikeflow.replay --check-every 24
python -m bikeflow.replay --check-every 24 --evening-boost 2.5 --boost-from 2018-11-01
```

В обычном потоке из 61 проверки дрейф модели не обнаруживается ни разу. С акцией в октябре всё
спокойно, а в ноябре дрейф модели срабатывает в 27 проверках из 30 — впервые 4 ноября, когда
ошибка достигает 1.8 от эталонной. Отчёт после прогона: <http://127.0.0.1:8000/drift/report>.

Перед повторным прогоном остановите API и удалите `data/predictions.db`: иначе в окно попадут часы
из обоих прогонов сразу.

### 8. Переобучение

Переобучение работает, когда API берёт модель не из файла, а из реестра MLflow: новая версия модели
регистрируется там, и API переключается на неё без перезапуска. Запустите API так (из корня проекта,
после шага 2 — обучение уже зарегистрировало модель с меткой `champion`):

```bash
BIKEFLOW_MODEL_URI=models:/bikeflow-demand@champion uvicorn bikeflow.api.main:app --port 8000
```

В PowerShell: `$env:BIKEFLOW_MODEL_URI="models:/bikeflow-demand@champion"`, затем `uvicorn ...`.

**Как проходит переобучение.**

1. Данные: исходный датасет до начала журнала плюс все часы журнала, для которых известен факт.
2. Последние 72 часа журнала откладываются для сравнения, 72 часа перед ними — для early stopping,
   на остальном обучается новая модель того же типа, что и текущая.
3. **Quality gate**: текущая и новая модель считают прогноз на отложенных часах. Новая заменяет
   текущую, только если её MAE ниже хотя бы на 5 %.
4. Любая новая модель записывается в MLflow как run и как версия `bikeflow-demand` с меткой
   `quality_gate` = `passed` или `rejected`. Метка `champion` переходит на новую версию только при
   пройденном gate — тогда API сразу начинает прогнозировать новой моделью.

Запускается двумя способами:

- **вручную** — `POST /retrain` (в Swagger или кнопкой в веб-интерфейсе);
- **автоматически** — когда `POST /drift/check` находит concept drift. Следующее автоматическое
  переобучение ждёт 72 часа новых данных, чтобы отклонённая модель не переобучалась на каждой
  проверке.

| Эндпоинт | Что делает |
| --- | --- |
| `POST /retrain` | запускает переобучение в фоне, ответ `202`; `409`, если уже идёт или API работает с файлом модели |
| `GET /retrain/status` | `running`, `finished` или `failed`; в `result` — MAE обеих моделей и решение gate |

Окна, порог gate и пауза между автоматическими переобучениями задаются в разделе `retraining`
файла `params.yaml`; `auto: false` отключает автоматический запуск.

**Демонстрация.** API запущен из реестра, в другом окне:

```bash
python -m bikeflow.replay --check-every 24 --evening-boost 2.5 --boost-from 2018-11-01
```

Поток ждёт окончания каждого переобучения и печатает решение gate. Результат такого прогона:

| Дата данных | MAE на отложенных часах: текущая → новая | Gate |
| --- | --- | --- |
| 4 ноября | 490 → 511 (−4 %) | не пройден |
| 7 ноября | 510 → 496 (+3 %) | не пройден |
| 10 ноября | 429 → 416 (+3 %) | не пройден |
| 13 ноября | 457 → 377 (+18 %) | пройден, в работе новая версия |

Первые модели ещё почти не видели акционных вечеров, поэтому gate их отклоняет. На часах после
переключения, 14–30 ноября, новая модель ошибается меньше старой: MAE 386 против 436. Все версии и
их метрики видны в MLflow UI (шаг 3).

### 9. Docker, Prometheus и Grafana

Сначала обучите модель (шаг 2): контейнер подключает готовый файл `models/model.joblib`.

```bash
docker compose up --build
```

Поднимаются три сервиса:

| Сервис | Адрес | Что там |
| --- | --- | --- |
| API | <http://127.0.0.1:8000/docs> | те же эндпоинты, что и локально |
| Prometheus | <http://127.0.0.1:9090> | собирает метрики API каждые 15 секунд |
| Grafana | <http://127.0.0.1:3000> | дашборд **BikeFlow**, вход не нужен |

Дашборд заведён заранее (`monitoring/grafana/`): дрейф модели, MAE окна против порога, прогнозы в
минуту по версиям модели, средняя ошибка присланных фактов, запросы по маршрутам и время ответа
`/predict`. Чтобы графики наполнились, пустите поток данных в контейнерный API:

```bash
python -m bikeflow.replay --api http://127.0.0.1:8000 --interval 0.2 --check-every 24
```

**Что отдаёт API.** `GET /metrics` — метрики в текстовом формате Prometheus:

| Метрика | Что показывает |
| --- | --- |
| `bikeflow_predictions_total{model_version}` | сколько прогнозов сделала каждая версия модели |
| `bikeflow_predicted_rentals` | распределение прогнозов |
| `bikeflow_actuals_total`, `bikeflow_absolute_error` | присланные факты и ошибка прогноза |
| `bikeflow_concept_drift`, `bikeflow_data_drift`, `bikeflow_target_drift` | результат последней проверки дрейфа |
| `bikeflow_window_mae`, `bikeflow_drift_mae_ratio`, `bikeflow_drift_mae_ratio_threshold` | ошибка за окно и порог срабатывания |
| `bikeflow_retrainings_total{outcome}` | переобучения: прошли gate, отклонены, упали |
| `bikeflow_http_requests_total`, `bikeflow_http_request_duration_seconds` | запросы и время ответа по маршрутам |

Значения дрейфа появляются после первой проверки `POST /drift/check`.

## CI

При каждом push в `main` GitHub Actions запускает:

- `lint` — проверка кода линтером ruff;
- `tests` — все тесты;
- `ml-tests` — тесты данных и модели;
- `docker-build` — сборка Docker-образа;
- `docker-runtime-smoke` — обучает небольшую модель, поднимает API в Docker и делает настоящий
  запрос к `/predict`.

## Ограничения

- данные за один год и по одному городу, без разбивки по станциям;
- тестовая выборка целиком осенняя, а осенних месяцев в обучении нет;
- хуже всего модель предсказывает часы пик и дождливые часы;
- погоду нужно передавать вручную — внешнего погодного сервиса нет.
